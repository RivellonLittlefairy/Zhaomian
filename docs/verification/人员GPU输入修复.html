人员 GPU 输入修复

2026-10-14 · 模型替换与已有日志核对

查到的问题

手机日志在 10-13 22:36:05 明确记录人员 GPU 推理失败：ToTensorConverter: input data size does not match expected size. 随后人员模型回退 CPU。CPU 对比时三个模型均显示 CPU，切换确实生效。

MediaPipe 0.10.21 的 TaskOptions 将 Delegate.GPU 转成 advanced GPU 配置。其图像预处理对 UINT8 输入强制走 CPU，而高级 GPU runner 的输入对象使用 FLOAT32。这与当前量化模型的输入适配错误一致；日志未记录实际和预期字节数，所以不将底层字节数差异当作已实测事实，也不声称所有量化模型都无法使用 GPU。

改动

  • 人员 GPU 使用官方 EfficientDet-Lite0 float16 v1；模型权重为 float16，实际输入是 FLOAT32 [1,320,320,3]。
  • CPU 对比和 GPU 失败回退仍使用原 int8 模型，其输入是 UINT8 [1,320,320,3]。
  • 模型创建时记录 backend 和 asset；运行成功后的阶段日志仍显示实际后端和耗时。
  • 维持抓拍规则、分析分辨率、目标采样率和停止行为。

新增模型：官方文件，7,254,339 bytes；SHA-256：4B59100025BEA1235A84C1038879A6CCCC9F6C49F5E41144E91E74D99E780993。随应用离线打包，不在运行时下载。

真机发现的类别过滤崩溃与修复

2026-10-14 09:22 真机日志显示 float16 人员模型创建成功，随后 GPU 后处理触发 SIGABRT：class_index_set_.values.size() ... (1 vs. 90) Only all classes >= class 0 or >= class 1。MediaPipe 0.10.21 的 tensors_to_detections_calculator.cc:1183 明确限制 GPU 只支持全部类别（或只排除背景），不支持单独 person 白名单。原生断言直接终止进程，Java/Kotlin 异常回退无法捕获。

修复：仅 CPU 路径保留 SDK person 白名单；GPU 路径不设类别过滤，结果继续由原有 Kotlin categoryName == person 且 score >= 0.6 筛选。抓拍条件保持不变。未改 SDK 或增加网络权限。OpenCL 库加载警告不是日志中终止进程的直接原因。

本轮 Debug / Release 构建结果见 docs/build-gpu-class-filter-fix.log；未自动安装或执行真机回归，仍需安装后确认 GPU 三模型分支能连续运行。
