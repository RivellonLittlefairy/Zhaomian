工程现在有什么

现有单 app 模块，包名 com.example.passerwatch，MainActivity 显示 Hello Android，已启用 Compose 和 Material 3。尚无相机、检测模型、抓拍或存储业务实现。

已读取源文件：app/build.gradle.kts、gradle/libs.versions.toml、MainActivity.kt、AndroidManifest.xml 等。当前只是静态检查，没有运行 Gradle 或真机测试。保留已有 Compose 主题，不迁移到 XML，也不另建工程。

后续文件按 ui/、camera/、detection/、capture/、monitor/、model/ 分工；模型放 assets，仍使用单 app 模块。

所有任务共用的规则

  • 技术路线：Kotlin、Compose / Material 3、CameraX Preview + ImageAnalysis、MediaPipe Object Detector、EfficientDet-Lite0 int8 CPU、ViewModel + StateFlow、协程 IO。
  • 第一版只在前台运行，检测时屏幕保持亮着；退后台或离开监测页面结束会话，返回后手动开始。旋转也按结束会话处理。
  • 推理初值最多 5 帧/秒、person 分数阈值 0.6、连续 2 个有效帧确认有人；超过 1 秒没有连续有效结果时重置确认。
  • 一次出现只触发一次；持续有效无人至少 2 秒才重新待命。检测异常、相机中断、没有处理帧都不是无人证据。
  • 图片使用对应检测触发帧的独立副本；完整画面不含 UI；不使用屏幕截图，也不另拍一帧替代触发帧。
  • 检测与保存分开；串行保存最多 1 张正在写入、2 张等待。队列满明确提示并释放多余图像，不阻塞检测。
  • 保存到 filesDir/captures，JPEG 质量初值 90，时间加唯一事件 ID 命名；临时写入成功后才变成最终 JPG。
  • 存储不足只暂停保存，检测继续，用户手动恢复，不补存；一般保存失败不对当前出现无限重试，不自动删除旧图。
  • 图片默认在 App 内查看；无需 Room、服务器、网络请求、推送、录像、历史列表、锁屏或后台服务。原始需求中的后续扩展暂不开发。
  • 依赖和模型使用固定版本；上述参数是调试起点，不是实测性能或准确率保证。

Compose 怎么和相机配合

MonitorScreen 负责页面；AndroidView + PreviewView 显示 CameraX 画面；CameraController / FrameAnalyzer 管相机帧；PersonDetector 识别人；CaptureGate 管出现与离开；CaptureSaveQueue / SnapshotStore 管保存；MonitorViewModel 把状态交给 Compose。

UI 状态走 StateFlow，图像不放进长期页面状态。相机和模型不要随重组反复创建；页面生命周期、监测会话、应用级保存任务各自管理，退出页面后已有保存可以收尾。

学习顺序跟任务走：02 学声明式 UI 与状态，03 学 AndroidView，06 学异步图片显示，11 学 remember、Effect 与生命周期。暂不引入复杂导航、依赖注入或多模块框架。

最容易漏掉的五件事

  1. 重组或相机异步初始化造成重复绑定、已离页又开启相机 → 任务 03、11。
  2. 帧方向、格式或资源释放出错，导致图片歪、相机卡住 → 任务 04、05。
  3. 短暂漏检或推理中断被当成人离开，造成重复抓拍 → 任务 09。
  4. 慢磁盘、空间不足、旧会话回调导致内存增长或错误状态 → 任务 10—14。
  5. 图片损坏、时间变化、重启或系统备份影响本地图片恢复 → 任务 05、06、15。

每项都在相应计划里有检查点；不用把所有界面细节变成自动化测试。

开始时还要核实

旧手机型号、Android 版本、ABI、可用空间、实际机位和光照尚未提供。任务 01 先记录设备信息；任务 07 确认模型兼容；任务 15—16 验证真实效果。没有设备时可以先做工程和规则，但不能把真机验收标为完成。
